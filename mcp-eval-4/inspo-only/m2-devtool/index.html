The four minutes after a red build

You already know the shape of this. Open the run, expand the failed job, scroll past nine hundred lines of setup.

Sightline does that scroll for you and gets to the same place you would have, except it starts the moment the job exits rather than the moment you notice.

01

It reads the run, not the summary

The exit code tells you a job failed. The output tells you why. Sightline ingests the full stream from every job, including the parts your CI truncates in the browser, and keeps it addressable.

Ranked by likelihood, not by line number.

candidate causes
selector renamed in this difflikely e2e runner out of memoryruled out flaky wait on network idleruled out upstream API 503ruled out

Each candidate is ruled out against something observable in the run, and the reasoning stays attached to the verdict.

02

It knows whether this test has failed before

The single most expensive question on a platform team is whether a red build is real. Sightline keeps the history of every spec across every branch, so a first-time failure and a spec that has been coin-flipping for weeks do not look alike.

Flakes get quarantined and reported. Real breaks get you.

Reading: clean history, one new failure. Sightline calls this a real break and does not offer a retry.

03

It puts the verdict where the failure already interrupted someone

The pull request, the deploy channel, the incident thread. Sightline routes by the code that changed rather than by whoever is on rotation, so the person who can fix it in one line is the person who hears about it.

One message per failure. No digest, no noise.

What it watches

Five things that are boring to track and expensive to miss.

None of this requires changing how your pipeline is written. Sightline reads what the run already emits.

Root cause

A build failure has one cause and about forty symptoms. Sightline is only interested in the cause.

It correlates the failing assertion against the diff in the run, the state of the runner, the dependency lockfile, and the last known green build, then names the one that explains the others. When it cannot pick a single cause it says so and shows you the shortlist instead of guessing.

Flake detection

Per-spec history, every branch

Failure rate by test, not by job. Quarantine on your rule, not ours.

Dependency drift

The build that broke without a commit

Lockfile changes, base image digests, and registry versions are diffed between runs.

Runner conditions

Out of memory, out of disk, out of time

Infrastructure failures get their own verdict class, because telling an engineer to debug their test when the runner ran out of disk is how a team learns to ignore your tool.

Verdict classes: code · test · dependency · infrastructure · unknown

Duration

Where the minutes went

Per-step timings across runs, so a slow pipeline has a suspect rather than a feeling.

Log reading

It does not summarise your logs. It finds the four lines that matter and shows its work.

A summary is a smaller version of a thing you did not want to read. A verdict is a claim you can check. Sightline links every claim back to the exact line and step it came from, so disagreeing with it takes one click, not a rerun.

Setup

One step at the end of the job you already have.

Sightline is read-only against your pipeline. It cannot cancel a run, rerun a job, or block a merge, and nothing about your build changes if you turn it off.

  1. Install the app

    Grant read access to the repositories whose pipelines you want watched.

  2. Add the reporting step

    It runs on failure and on success, because a verdict needs to know what green looks like here.

  3. Choose where verdicts land

    Pull request comments are on by default. Everything else is opt-in.

  4. Break something on purpose

    The fastest way to trust a diagnosis tool is to hand it a failure you already understand.

# .github/workflows/ci.yml
- name: Report to Sightline
uses: sightline/report@v1
if: always()
with:
token: ${{ secrets.SIGHTLINE_TOKEN }} # or, from any CI that can run a binary
$ sightline report --job "$JOB_NAME" --exit $?

Reasonable objections

The questions a platform engineer asks in the first five minutes.

Asked in roughly this order, every time.

What happens when it is confidently wrong?

It marks the verdict disputed and stops offering that explanation for this failure class until it has seen a resolution. Every verdict shows the evidence it used, so a wrong call is visible as a wrong call rather than as a vague suggestion you cannot argue with. A tool that cannot be corrected gets ignored within a fortnight.

Does my source code leave my infrastructure?

Log output and diff hunks for the failing paths do. Full source does not. There is a self-hosted deployment for teams whose answer to that first sentence is still no, and a redaction pass that strips values matching your secret patterns before anything is stored.

We already have dashboards for this.

Dashboards tell you the failure rate is up. They do not tell you the checkout spec is waiting on a button that got renamed. Sightline is not trying to be the place you look; it is trying to be the thing that arrives before you go looking.

Our pipeline is unusual.

Most of them are. The reporting step is a binary that takes a stream and an exit code, so anything that can run a shell command can report. Custom verdict classes are configuration, not a support ticket.

Start

Connect one pipeline. Break it on purpose. Read the verdict.

That is the whole evaluation. If the verdict is not better than your own first guess, you will know within an afternoon.
