AN OPEN-SOURCE JOB QUEUE FOR NODE.JS

Your job queue is a file.

Windlass gives your app durable background jobs backed by a single SQLite file. No Redis to run, no broker to keep alive, one dependency in the lock file. Install it, hand it a path, enqueue.

$npm install windlass

or start with the five-minute guide

MIT license · Node 18+ · TypeScript types · zero services

/ HOW IT WORKS

A queue is a table. A job is a row.

Enqueueing is an INSERT. Claiming a job is one transaction, so two workers never take the same row. WAL mode keeps writers from blocking readers. Everything Windlass knows lives in one file you can copy, back up, and open in sqlite3 when you get curious.

Not in this architecture: redis-server a message broker a queue dashboard VM an on-call page for the queue
You deploy your app. The queue travels with it.

/ WHAT YOU GET

A small surface that does the whole job.

01

Durable by default

Every job is a row on disk before add() returns. Kill the process mid-run and nothing is lost: unfinished work is claimed again the moment a worker comes back. Finished jobs keep their history until you prune it.

02

Later, or every Monday

Delay jobs, or give a queue a repeat rule and let it re-arm itself.

{ delay: "2h" } { repeat: "mon 09:00" }
03

Retries with backoff

Attempts per job, fixed or exponential backoff, and a dead-letter state that keeps failures where you can inspect and requeue them.

04

Concurrency you choose

Set worker count per queue. Priorities jump the line; everything else is first in, first out.

05

One dependency

Windlass depends on the SQLite driver and nothing else. Your node_modules stays recognisable, your audits stay short.

06

Events, if you want them

Lifecycle hooks for done, failed and drained. Wire them to your logger or your pager, or ignore them entirely.

queue.on("failed", notifyOps); queue.on("drained", logIdle);
07

Inspect with SQL, or the CLI

No dashboard to host: the queue is a table, so your questions are queries.

$ npx windlass ls ./data/jobs.db

queue            waiting  running  retry  done
email.welcome    2        1        0      114
invoice.pdf      0        1        1      89
/ THE HONEST PART

Where it fits. Where it does not.

Reach for Windlass when

  • your app and its jobs deploy together, on one or two boxes
  • the work is emails, exports, webhooks, PDFs, cleanup
  • you would rather back up a file than operate a service
  • a queue outage should never be its own incident

Keep a server queue when

  • many app servers must share one queue over the network
  • you need pub/sub fanout to other services
  • workers must scale horizontally across machines
  • jobs must outlive the machine itself: a file dies with its disk

Most side projects and most small products live entirely in the first column. Windlass is built for them, and it will tell you, in the docs and here, when you have outgrown it.
