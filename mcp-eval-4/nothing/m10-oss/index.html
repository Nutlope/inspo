Background jobs, backed by a file.

Windlass is a job queue for Node.js that keeps every job in a single SQLite database. Durable, transactional background work with retries, scheduling and a dead-letter table: no Redis to run, no broker to babysit, one line in your lockfile.

SQLite WAL mode · at-least-once delivery · exponential backoff · cron repeats · dead-letter table · zero daemons

Durable the moment add() resolves. Retried on a curve. Yours to query.

01 · Working theory

The queue is a database you already trust.

A background queue should not be the most operationally demanding thing you run.

The standard recipe for background jobs in Node is a Redis instance, a connection pool, a worker fleet and a dashboard to keep watch over all of it. At forty engineers, that is Tuesday. For one person shipping a product, it is a second job with worse hours.

Windlass takes the other road. A job is a row. Enqueueing is an INSERT. Claiming work is a single UPDATE inside a transaction, so two workers can never hold the same job, even across processes. Everything the queue knows lives in one file you can copy, back up with the tools you already use, or open in the sqlite3 shell when curiosity strikes.

02 · Capabilities

Everything a queue owes you.

And nothing a fleet demands.

01

Durable by default

Every job lands in SQLite before add() resolves. Kill the process, trip over the power cord, deploy mid-batch: the work is still there when you come back.

02

Transactional enqueue

Add jobs inside the same transaction as your own writes. If the order commits, the receipt job exists; if it rolls back, the job never happened. No outbox, no drift.

03

Retries with backoff

Failures retry on an exponential curve with jitter, up to the cap you set. After the last attempt the job moves to a dead-letter table you can query and requeue, not a black hole.

04

Scheduling and repeats

Run a job in ten minutes, at 02:00, or on a cron expression. Delayed and repeating jobs sit in the same file as everything else, and survive restarts like everything else.

05

Concurrency and rate limits

Cap concurrency per queue, or per key within a queue: four renders at once, never two exports for the same customer. Backpressure is a setting, not an incident.

06

Observability in plain SQL

It is a database, so SELECT is your dashboard. Count the backlog, chart throughput, join jobs against your own tables. Any SQLite browser is a queue UI.

03 · Night watch

Keep watch from any shell.

The questions you actually ask a queue are small: what is waiting, what is failing, and what did it say when it failed. Windlass ships a three-command CLI for exactly those.

Past that, the file is the API. Point any SQLite browser, BI tool or backup script at jobs.db and it simply works, because rows are rows.

  • windlass statusthe shape of the backlog, per queue
  • windlass retrysecond chances, one job or all of them
  • windlass tailfailures streaming live, with the error that caused them
~/acme-appexample session
$ npx windlass status ./data/jobs.db

  invoice.render        12       4     214       3
  email.welcome          0       1     962       0
  export.csv             2       0      31       1

$ npx windlass retry export.csv --dead

04 · Load line

Honest about its load line.

Ships carry a painted mark showing how deep they may safely sit in the water. Tools should carry one too. Windlass states its plainly, and floats best below it.

Made for

  • Products that live on one box, or a few with a shared disk
  • Email, exports, thumbnails, webhooks, cleanup: the everyday cargo
  • Teams of one to ten who would rather ship than operate
  • Apps where every job must survive a deploy or a crash

Not for

  • Workers spread across many machines with no shared disk
  • Fan-out so hot that a single writer becomes the ceiling
  • Multi-region delivery with strict latency budgets
  • Teams already running Redis happily: keep it

Outgrowing the file is a milestone, not a trap. windlass export writes newline-delimited JSON that whatever comes next can drink.

05 · Quickstart

Weigh anchor in three moves.

STEP 01

Install

$ npm install windlass

Your lockfile grows by one line. That is the whole ops story.

STEP 02

Define and add

queue.work("email.welcome", sendWelcome);

await queue.add("email.welcome", { userId: 42 });

Jobs persist before add() resolves, and survive anything short of losing the disk.

STEP 03

Start workers

queue.start({ concurrency: 4 });

In the process you already run, or one of its own. Both restart clean.

Your app has work to do.

The whole thing is smaller than the ops doc you were about to write.
