The part nobody schedules

A build breaks and the day bends around it.

CI tells you that something failed. Working out what failed, and whether it is even your fault, is still a manual job that lands on whoever is nearest the pipeline. Usually you.

  1. 01

    A red check appears on a pull request with no explanation beyond an exit code.

  2. 02

    Someone opens the raw log and starts scrolling for the first line that looks angry.

  3. 03

    They rerun it, because half the time reruns go green and nobody knows why.

  4. 04

    It fails again. Now it gets posted in the platform channel.

  5. 05

    You read the log instead. This is the fourth time today.

How it works

Three moves, none of them in your runner.

Sightline connects to the CI provider you already have. It reads what the pipeline emits, compares it against everything that ran before, and writes the conclusion down.

01 Watch

Watch every run, not just the red ones

Logs, step timings, exit codes, runner metadata and the diff attached to each run. Green builds are the control group: without them there is nothing to compare a failure to.

ingest run.completed
steps 14 · 13 pass · 1 fail
diff 3 files, 2 services

02 Correlate

Ask what changed, not what printed

The failing step gets lined up against the last run that passed, the same job on other branches, and the change set in between. Most root causes fall out of that comparison rather than out of the stack trace.

parent pass
this fail
others pass on 6 branches
delta ci/compose.yml

03 Verdict

Write the reason where the work is

One paragraph in the pull request, the chat thread, or the terminal. Cause, evidence, and whether this is code, infrastructure, a flake or an upstream problem. Disagree and the verdict takes the correction.

post pull request comment
class infrastructure
owner platform
action restore healthcheck
Anatomy of a verdict

Short enough to read on a phone. Specific enough to act on.

A verdict is not a summary of the log. It is a claim about why the build broke, with the evidence that supports it and an honest note when the evidence is thin.

  • The claim, in one sentence

    Written for someone who has not opened the pipeline yet and would rather not.

  • Code, infrastructure, flake or upstream

    The classification decides who picks it up. Most of the arguing in a platform channel is really about this line.

  • The evidence, not the whole log

    The handful of lines that carried the signal, plus the comparison runs that make them meaningful.

  • Confidence you can argue with

    When two causes fit equally well, Sightline says so and shows both instead of picking the confident-sounding one.

  • A correction path

    Mark a verdict wrong and the reason feeds back into how the next one is written for that pipeline.

sightline commented on this pull request
Integration tests failed for a reason that is not in this diff's test code.
cause infrastructure confidence high, single explanation fits step integration (timed out)
evidence connection refused postgres:5432 repeated for the first 30 attempts, then the step's own deadline hit parent commit same suite, passed six other branches same suite, passed
changed ci/compose.yml -8 +2 the healthcheck and depends_on condition were removed together
so the suite now starts before the database is accepting connections. Restore the wait or move it into the test harness.
Wrong? Reply not it and say why.

What it reads

The failures that eat a platform team's week.

Different causes leave different fingerprints. Sightline is built around the ones that repeat, because those are the ones your team has learned to dread.

Flakes, named as flakes

A test that fails on this run and passes on the same code elsewhere gets called what it is, instead of sending someone hunting through a diff that is innocent.

Runner and environment drift

Image bumps, disk pressure, exhausted memory, a service container that never became ready. Failures that belong to the platform and not to the pull request.

Dependency and lockfile shifts

When a transitive bump is the only thing separating a green run from a red one, that is the headline, not a line buried in an install step.

Timeouts with a real subject

A step that ran out of time is a symptom. Sightline reports what it was waiting on and whether the wait has been getting longer.

Failures that cross repositories

When the same break appears in several pipelines within the hour, it is grouped into one incident with one cause rather than five separate mysteries.

The slow rot, before it breaks

Steps drifting toward their timeout, caches missing more often, a suite that gets a little redder every week. Trends surface while they are still cheap to fix.

Q1 What does it actually need access to?

Build metadata, logs and the diff for each run, read-only. It does not need write access to your repositories, and it does not need credentials that can start or cancel builds.

Q2 Do logs leave our infrastructure?

Your choice. The cloud version stores logs for a retention window you set. The self-hosted version keeps everything inside your network and only reaches out for licence checks.

Q3 What happens when the verdict is wrong?

You mark it wrong and say why, in the same thread. The correction is kept alongside that pipeline and shapes how later failures of the same shape are read. Wrong verdicts are worth more to us than silent ones.

Q4 Does it work on a pipeline nobody has cleaned up?

That is the normal case. Sightline does not require structured output, a particular test reporter, or tidy step names. It gets sharper when those exist, but it does not wait for them.

Q5 Who on the team sees what?

Verdicts follow the permissions of the repository they belong to. Pipeline-wide trends and cross-repository incidents are scoped to the teams you grant them to.

Point it at one noisy pipeline and see what it says.

Start with the repository that generates the most questions. If the verdicts are not better than reading the log yourself, disconnect it and nothing about your CI has changed.
